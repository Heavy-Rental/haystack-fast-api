**Day 6+ (future, not part of the original 5-day build) — Phase 2d: guardrail/duration-discount scale calibration** (new 2026-08-11, found during Phase 2a's live verification)
- **Finding**: live-testing `predict_price(...)` against all 27 real `heavy_rental` assets showed the raw model output falls **below** `Asset.minDailyRate` for nearly every asset at a typical rental duration — 25 of 27 assets clamped upward at `duration_days=7`. At `duration_days=1` (no duration discount applied) the picture is very different and much more mixed: 18 of 27 clamped, in both directions, not just up. This points to a scale mismatch, not randomness: the model was trained with a non-linear duration discount (price drops for longer rentals, by design — down to ~0.35x at long durations, see `ml-experiments/pricing_tables.py`'s `DISCOUNT_FLOOR`/`DISCOUNT_RATE`), but the real seeded `minDailyRate`/`maxDailyRate` bounds look like they represent a near-1-day rate floor/ceiling, not a duration-adjusted range. For any multi-day rental — i.e. most real bookings — the guardrail clamp is currently overriding most of the model's duration signal rather than lightly bounding it.
- **Not a Phase 2a defect.** Guardrail clamping does exactly what spec.md requires: clamp raw output to `[minDailyRate, maxDailyRate]`. This is a data/model calibration question the spec never anticipated, surfaced only once real per-asset bounds (this reseed) and real per-asset clamping (Phase 2a) both existed to reveal it — neither alone would have shown it (static category-table guardrails were too coarse; the old 8-asset fixture too thin to see the pattern clearly).
- **Why it matters**: it undercuts the "meaningful, differentiated pricing" goal the seed-data richening (`openspec/specs/domain-seed-data/spec.md`) was specifically for — if the guardrail clamp dominates at realistic durations, two assets with very different `condition`/`capacity`/`period_utilization` can still converge on the same clamped price (their shared `minDailyRate`), which is close to what richer seed data was meant to avoid.
- **Options evaluated**:
  1. ✅ **Chosen** — retrain against a synthetic dataset re-anchored so the discount curve operates within the real guardrail band, rather than falling below it.
  2. ✅ **Confirmed 2026-08-12** — `Asset.minDailyRate`/`maxDailyRate` are meant to bound the price at any duration, not a 1-day-only reference rate.
  3. ❌ **Ruled out** — moot once Option 2 confirmed the any-duration semantics: `model.py`'s existing clamp already applies uniformly regardless of `duration_days`, which is correct for that interpretation; no duration-aware clamp change needed.
- **Verification target**: a materially lower clamp rate at realistic demo durations (7–14 days), not just at `duration_days=1`.
- **Decided 2026-08-12: proceeding with Option 1 (retrain), broken into three smaller sub-phases plus a separately-gated promotion phase** — none of the sub-phases below touch the existing tracked `app/services/pricing/artifacts/model.pkl`/`current.json` or `ml-experiments/data/synthetic_pricing_data.csv`; every regenerated/retrained artifact goes to a new, versioned path alongside the originals. Full rationale and the two-knob mismatch-check approach: masterplan "Phase 2d — retrain approach".
- **`ml-experiments/` restructured into per-round subfolders (2026-08-12)**, so this new round's generated files never sit flat alongside the Phase 1 baseline: `ml-experiments/{data,outputs,artifacts}/phase2d/` (new, `.gitkeep`-tracked under `data/`/`outputs/`, matching the existing convention — `artifacts/` never had a `.gitkeep`, whole dir is gitignored regardless). `.gitignore`'s `ml-experiments/data/*.csv`/`ml-experiments/outputs/*.png` rules widened to `**/*.csv`/`**/*.png` so the new subfolder's generated files stay ignored too. Nothing existing moved — none of `data/`, `outputs/`, `artifacts/` was git-tracked to begin with (only `.gitkeep` placeholders were), so this is pure local file organization, zero risk to the Phase 1 baseline.
