## Locked decisions

### Target variable & features
- **Target: `price_per_day`**, not `total_price`. App-layer computes `Booking.total_amount = price_per_day × duration_days (+ fees)` — this is business logic, not the model's job.
- **Duration**: continuous numeric feature `duration_days`. No `duration_tier` category — rate-card/tiering was removed from the schema (`Asset` just has `baseDailyRate`/`minDailyRate`/`maxDailyRate`), so let XGBoost learn the discount curve directly.
- **Category**: one-hot encode `AssetCategory.name` (forklift / boom lift / scissor lift / excavator), joined from `Asset.category_id → AssetCategory`. **Never** feed the raw `category_id` FK integer into the model or encoder — it's an arbitrary, unstable identifier, not an ordinal or meaningful numeric value.
- **`vehicle_vs_static` flag: dropped.** All 4 categories are vehicles — zero signal, not worth encoding.
- **`operator_required`: removed from scope entirely.** Not tracked as a concept anywhere in the project (not just the pricing feature) — simplification decision, not a data gap. Do not add it as a feature.
- **`condition` (`Asset.condition`): included as a feature.** Ordinal, not nominal — encode as an integer scale (`NEEDS_REPAIR=0, FAIR=1, GOOD=2, EXCELLENT=3`), not one-hot, since the levels have a real order the model should exploit directly. Use it as a second sanity check in the Phase 1 SHAP review, alongside duration: worse condition should pull predicted price down, holding category/duration fixed.
- **Delivery distance: new numeric feature `distance_km`, included.** Distance from the equipment yard (Tuas, postal 629462) to the job site, with a real (small, monotonic) effect on `price_per_day` — not a passthrough column. **Phase 1: sampled directly from a realistic right-skewed distribution, same approach as `duration_days`** — not computed from two coordinates and not derived from real postal codes. No geocoding call (OneMap or otherwise) in this phase. Real address-based geocoding is explicitly deferred to a later phase; see the now-updated `Booking` fields note below.
- **`platform_height`: added to scope mid-Phase-1b, not part of the original Day 2-3 feature list.** The baseline model (category/condition/duration_days/capacity/distance_km only) looked fine on overall holdout metrics, but a per-category MAE/R² breakdown showed boom lift/scissor lift fitting dramatically worse than forklift/excavator (R² 0.70/0.80 vs 0.95/0.96) — consistent with `capacity` being a secondary dimension for aerial lifts, where platform height is what actually drives rate-card price. Added `platform_height` as a numeric feature; it's structurally missing (not just noisy) for forklift/excavator, which have no platform. **Locked as NaN, not imputed to a sentinel like 0** — XGBoost's native missing-value handling (a learned per-split default direction) is the correct tool for "not applicable," whereas an imputed 0 would teach the model a specific, misleading height for equipment that has none. Closed the per-category error gap: overall R² 0.94→0.98, all four categories to R² 0.95-0.97 after retraining.
- **`period_utilization` (Phase 1d, implemented; status filter/overlap rule confirmed 2026-08-09): the model's first real-time signal.** Fraction of same-`category`+spec-band assets already booked over the requested window — live aggregate at prediction time, not a forecast. **Status filter: `{PENDING_DEPOSIT, PENDING_CONFIRMED, CONFIRMED, MOBILISED}`, excluding `COMPLETED` and `CANCELLED`** — confirmed with the booking-flow owner that equipment is held for the customer from `PENDING_DEPOSIT` onward (deposit isn't a prerequisite for the hold). `COMPLETED` is excluded because the asset has been returned; `CANCELLED` is excluded because cancellation releases the hold on the calendar — cancellation is a real, reachable status (corrected 2026-08-09; initially assumed happy-path-only, which was wrong — see the `Booking` schema-fields entry below). **Overlap rule: inclusive on both boundaries** — confirmed the product rule is that two rental windows on the same asset conflict if they share *any* day, including matching start/end dates (no same-day turnover, kept simple deliberately) — this must match `BookingAvailabilityFilter`'s existing `a_start <= b_end and b_start <= a_end` check exactly, not a half-open convention. Spec-band avoids a fully-booked small-excavator fleet making a large excavator look scarce: excavator/forklift bucket on `capacity`, scissor/boom lift on `platform_height`, via `pricing_tables.CAPACITY_BINS`/`HEIGHT_BINS` — fixed constants grounded in real load-class/aerial-height-tier conventions, no persisted band column. Full rationale + exact values are in that file's comments now, not repeated here. **Not a bug**: an early booking on an unclaimed window legitimately prices lower (airline/hotel-style scarcity pricing) — don't "fix" this.
- **`lead_time_days` (Phase 1d, implemented)** — `Booking.startDate − today`, derived, no new column. Kept alongside `period_utilization` despite being correlated by construction (they answer different questions) so SHAP can show which the model leans on more — see "SHAP importance tuning" below.
- **Fuel price: considered and rejected (Phase 1d).** Indirect/lagged signal (fuel → construction activity → demand, not per-booking), would need a new external API dependency (breaks the in-process/no-outbound-calls architecture), and would be untrainable noise on synthetic data without fabricating a correlation.
- **SHAP importance tuning (Phase 1d).** Both new features initially came out low-importance (2.29/2.26) and heavily entangled (`corr` -0.59, since `period_utilization` was generated as a near-linear function of `lead_time_days`). Fix, in two steps, each verified via `shap_review.py --strict` + `category_metrics.py` (no regression at any point): (1) halved `LEAD_TIME_UTILIZATION_SLOPE` 0.006→0.003 to reduce the entanglement (`corr` → -0.35) — this alone didn't raise combined importance (4.55→4.30), since decoupling only cleans up *attribution* between the two features, not the total price-moving magnitude; (2) bumped `FIRMNESS_SLOPE` 0.15→0.21 and `LEAD_TIME_URGENCY_SLOPE` 0.0015→0.0021 (1.4x each) to actually raise that magnitude. Final: `period_utilization` 2.51, `lead_time_days` 3.18 (combined +25%), still well below `duration_days`(40)/`capacity`(47)/`condition`(14) — deliberately: a rental price driven more by *when* you book than *what* you're renting would be a red flag. Guardrail clamp rate barely moved (8.9%→8.8%) despite the bump.

### Relevant schema fields (from ERD / Class Diagram, 2026-08-03 versions)
Only the fields that matter for pricing — not the full schema. Field names as shown in the diagrams; confirm exact casing against the actual SQLAlchemy/JPA models when you get there.

**AssetCategory**
- `id` (PK)
- `name` — join target for category one-hot encoding (forklift / boom lift / scissor lift / excavator)

**Asset** (real columns confirmed snake_case, 2026-08-09, against `postgres-haystack`/`postgres-primary` — camelCase names below are the original diagram-sourced names, kept for cross-reference)
- `id` (PK), `category_id` (FK → AssetCategory) — always join to `name`, never encode the raw FK
- `capacity` (int) — numeric feature; drives base price scaling *within* a category (e.g. bigger excavator = higher rate). **Confirmed nullable, and currently null for every excavator/scissor-lift/boom-lift row** in seed data (populated only for forklifts) — a DB cleanup to backfill it is planned, but `model.py` keeps a permanent fallback regardless: per-category midpoint from `pricing_tables.CATEGORY_CAPACITY_KG`, applied to both the model feature and `spec_band()` bucketing. **Deliberately not NaN-passthrough** like `platform_height` — this is a data-entry gap, not a structural absence (the excavator does have a real capacity), and the synthetic training data always has `capacity` populated per category, so a NaN input would be out-of-distribution for the trained model rather than triggering calibrated missing-value routing.
- `baseDailyRate` (`base_daily_rate`) — reference point for realistic base-price ranges in the generator
- `minDailyRate` / `maxDailyRate` (`min_daily_rate` / `max_daily_rate`) — the guardrail bounds; also exactly the range the trained model's output gets clamped to at inference time (see Architecture section below). Confirmed `NOT NULL` — always present, no null-handling needed.
- `condition` (`ConditionType`: EXCELLENT / GOOD / FAIR / NEEDS_REPAIR) — **locked in as a feature.** Ordinal encoding (`NEEDS_REPAIR=0 … EXCELLENT=3`), not one-hot — see Target variable & features section above. **Confirmed nullable** (`SPEC-spring-entity-repository.md` §5.3, 2026-08-09) — current seed data happens to have it populated for all 8 assets, but `feature_schema.encode_condition()`'s `.map(CONDITION_ORDER).astype(int)` crashes (`ValueError`) on a null today, since there's no unmapped-value handling. **Fallback locked: `"GOOD"`**, not NaN — same reasoning as `capacity` (a data gap, not a structural absence; training data always has `condition` populated, so NaN would be out-of-distribution) — and moot anyway, since the ordinal `astype(int)` cast has no way to represent NaN. `"GOOD"` chosen as the neutral middle-of-scale default (ordinal 2 of 0–3) rather than skewing toward either extreme.
- `purchaseYear` (int) — optional proxy for equipment age; only add if `condition` alone doesn't capture enough signal. **Not added** — Phase 1b's condition SHAP check passed cleanly (0% adjacent-step violations) with `condition` alone, so this wasn't needed. Not rigorously ablation-tested; revisit if a future retrain shows `condition` under-capturing age effects.
- `platform_height` (numeric, meters) — **added in Phase 1b, not part of the original 2026-08-03 field list.** Present only for scissor lift/boom lift (null for forklift/excavator); see the locked-decision entry above for why and how it's encoded. Confirmed as a real column, 2026-08-09.

**BookingItem**

- `subtotal` — composed from `daily_rate × duration`, i.e. what `total_amount` math draws from

**Booking**

The equipment is held for the customer from `PENDING_DEPOSIT` onward, confirmed with the booking-flow owner; a `CANCELLED` booking releases that hold.

**RecommendationItem**

### Reference basis for synthetic data (Phase 1)
- **Base pricing figures**: real company rate cards (Pollisum, Ben's Rental) + general industry rate-guide benchmarks — duration discounting is non-linear (weekly ≈ 3–4× daily, monthly ≈ 10–12× daily, not a flat 7×/30× multiple).
- **Seasonality**: NEA monsoon calendar (NE monsoon Dec–Mar wettest → suppresses outdoor/earthmoving demand) + BCA quarterly construction-demand data (Q4 contract-award spikes from public housing/institutional pipelines).
- **Utilization bands by category**: fleet-KPI industry benchmarks — aerial (scissor/boom lifts) ~72–80%, blended/general ~65–72%, earthmoving (excavators) ~55–62%, generators up to 80%+ in peak periods.
- Keep a short "References" docstring at the top of `generate_synthetic_data.py` citing these — cheap insurance against "did you just make these numbers up?"

### Architecture (Phase 2)
- **Package placement**: `app/services/pricing/` subpackage — `model.py`, `train.py`, `feature_schema.py`, `artifacts/` (holding `.pkl` files + `current.json`). Not a separate top-level `ai_service/` — stays inside the existing `app.services` layering.
- **Where the prediction lands**: `predict_price(...)` returns the prediction in the recommendation response only. The pricing call is **internal-only** — never a public/renter-facing route. (2026-08-11 addendum: this still holds for the recommendation pipeline's call path. A separate internal service-to-service HTTP endpoint, `POST /internal/v1/pricing/quote`, was scoped the same day for Spring Boot's checkout flow — it's a new consumer of the productionized pricing service, not a reversal of this decision; see "Internal pricing quote API" below.) **Haystack does not persist it** — Spring Boot persists the returned value to `RecommendationItem.mlPredictedPrice` on its side. Agreed in principle 2026-08-10, **locked 2026-08-11** (Spring Boot confirmed); see "Persistence: Haystack does not write `mlPredictedPrice`" below and the change log entries for both dates. Pricing's DB access is read-only as a result — no code path in this service writes to Postgres. This rests on every prediction happening inside a synchronous Spring Boot → Haystack request, so a response always exists to carry the value back; re-check if a batch/offline re-pricing path (e.g. a Phase 3 retrain that re-prices existing rows in bulk) is ever planned.
- **Prediction call shape: in-process Python function call, not an HTTP endpoint.** Decided once ownership of both the pricing service and the agentic pipeline's calling code landed with the same person, closing the earlier "TBD" — no cross-team contract to negotiate, so no need for the overhead of a real HTTP route (auth, serialization, separate test client). Lives in `app.services.pricing` and is called directly from `app.pipelines` (or wherever the agentic pipeline's recommendation step lives). Revisit only if the pipeline ever needs to run as a decoupled/separate service — not a goal for this build.
- **Guardrails**: `Asset.minDailyRate` / `Asset.maxDailyRate`, admin-editable per asset via the admin portal's asset tag. The service reads the specific asset's row and clamps the model's raw output to that range at prediction time. No separate env var or config table needed.
- **DB access**: sync SQLAlchemy + `psycopg` only, per the setup constitution. No async wiring for this feature. Bare `DATABASE_URL` schemes are normalized per project-setup (`postgresql+psycopg`).
- **Read resilience (2026-08-10)**: every pricing read against `primary_snapshot` shares one 3-tier fallback (retry on transient mid-recreate failure → degrade to reading `public` on sustained failure, marked degraded → fail loud on cold start), decided once per `predict_price()` call, not per query. Full design: `openspec/specs/dynamic-pricing/design.md` ("Read resilience: tiered fallback"), canonical — not restated here. Scoped into Phase 1e, not deferred to Phase 2.
- **Migrations**: no Alembic. Pricing reuses existing `Asset`/`Booking`/`BookingItem`/`AIRecommendation` schema — doesn't create new tables, so no migration story needed on the FastAPI side at all.
- **Data source schema (discovered 2026-08-09, corrected 2026-08-10)**: `postgres-haystack`'s `heavy_rental` database exposes two schemas — `primary_snapshot` (`postgres_fdw` foreign tables reading live from `postgres-primary`'s real `public` schema, the actual Spring-Boot-owned data) and `public` (a separate local table set). **Correction:** this entry originally said the two "currently hold identical rows, but nothing keeps them in sync" — that's wrong. An external job (outside this repo) periodically merge-upserts `postgres-primary → public` keyed by primary key, so `public` is a lagged copy (at most one sync cycle stale), not an arbitrarily-drifting fork — it still accepts direct writes, but any row sharing a primary key with upstream gets those writes overwritten on the next cycle. Full mechanics and the fallback-relevant consequences now live in `openspec/specs/dynamic-pricing/design.md` ("Data access"), canonical for this topology — not restated here. **All pricing SQLAlchemy models must set `schema="primary_snapshot"`**; SQLAlchemy's default search path resolves to `public`, which would silently read the stale copy otherwise.

### Persistence: Haystack does not write `mlPredictedPrice` (2026-08-10, locked 2026-08-11)

**Decision**: Haystack does not persist `ml_predicted_price`. `predict_price(...)` returns the price in the recommendation response (`item.pricing.daily_rate`), and Spring Boot persists it to `RecommendationItem.mlPredictedPrice`. Pricing's database access becomes **read-only** — no code path in this service writes to Postgres. **Status: locked (2026-08-11)** — Spring Boot confirmed; no longer agreed-in-principle only. Pricing's Postgres role can now be granted `SELECT` only.

**Why**, not just the outcome:

1. **It's their column.** `mlPredictedPrice` is a JPA-mapped field on a Spring Boot entity (`SPEC-spring-entity-repository.md`: `mlPredictedPrice` → `ml_predicted_price`, `BigDecimal`, nullable), in a schema this masterplan already says Spring Boot owns (schema + migrations). The current design has Python writing a column a JPA entity manages — two writers, one unaware of the other. A Spring-side entity flush can overwrite Haystack's value on its own, independently of any sync behaviour.
2. **It removes pricing's only write.** `openspec/specs/dynamic-pricing/design.md`'s data-access section listed reads for `assets`/`bookings`/`asset_categories` "plus write access to `recommendation_items.ml_predicted_price`." Drop that one write and pricing is a pure reader — at which point read-only stops being a naming convention and becomes enforceable as `GRANT SELECT`. This matters because the `primary_snapshot` foreign tables are writable (`pg_relation_is_updatable = 28`) and point at the Spring Boot production database, so a stray SQLAlchemy autoflush on a mutated instance can currently write upstream.
3. **It dissolves the write-target dilemma.** Writing to `public.recommendation_items` gets clobbered by the sync's merge-upsert, which sets every shared non-key column to `EXCLUDED` each cycle, including to `NULL`. Writing to `primary_snapshot.recommendation_items` writes into the Spring Boot production table directly. Neither is a safe home for a prediction. Not writing at all removes the question.
4. **It removes an ordering problem.** For Haystack to set that column the `recommendation_items` row must already exist — so Spring Boot inserts, then Haystack updates, requiring ordering guarantees, row-not-yet-present handling, and recovery when the update fails after the insert committed. If Spring Boot persists, the price lands in the same unit of work that creates the row.
5. **The plumbing already exists.** `item.pricing.daily_rate` is a locked response field (`SPEC-agentic-equipment-recommendation-and-pricing` FR-012, `SPEC-recommendation-pipeline` FR-P-011). The value already crosses the wire — this removes a write that was never built, rather than adding transport.
6. **It aligns with a principle already stated for bookings** (`openspec/specs/domain/spec.md`, "Booking availability is read-only"): this service treats bookings as read-only and does not own their write path. A Haystack write to a Spring-owned entity is the same category of violation that principle exists to prevent.

**Assumption this rests on** (state explicitly, re-check before relying on it): every prediction happens inside a synchronous Spring Boot → Haystack request, so there is always a response to carry the value back. Confirmed 2026-08-10: the only route reaching the pipeline is a synchronous request/response endpoint. This would be the wrong call if a batch or offline re-price path is ever planned — e.g. a Phase 3 retrain that re-prices existing `RecommendationItem` rows in bulk. Nothing commits to that today, but nothing rules it out either — flag it as the premise to re-check with whoever owns the roadmap before Phase 3 planning locks in.

Full spec-level statement: `openspec/specs/dynamic-pricing/spec.md` (Outcomes, "Surface pricing on recommend items", Implementation tasks) and `openspec/specs/dynamic-pricing/design.md` ("Data access"). Task-level consequence: `dynamic-pricing-execution-plan.md` Phase 2b — "wire into pipeline → persist" becomes "→ return in response"; the persistence task moves to the Spring Boot side.

### Internal pricing quote API (2026-08-11)

**Decision**: add `POST /internal/v1/pricing/quote`, a synchronous, service-to-service HTTP endpoint (Spring Boot → Haystack) returning an authoritative, guardrail-clamped price per asset at checkout. Proposed by Spring Boot alongside a proxy endpoint for React; Haystack only needs to build the Spring-facing side. Full request/response contract and rationale for each sub-decision: `openspec/specs/dynamic-pricing/design.md` "Internal quote API"; normative requirement: `openspec/specs/dynamic-pricing/spec.md` "Requirement: Internal pricing quote endpoint (US-4)".

**Why this doesn't reverse the "in-process only" decision above**: that decision was about the recommendation pipeline's own call path (same-owner, no cross-team contract needed). This is a genuinely new consumer — a different service, at a different point in the flow (checkout, not recommend) — that Phase 1's design never anticipated. It's still never renter-facing (only Spring Boot's backend calls it) and still reuses the same `predict_price(...)` — no duplicated ML/pricing logic.

**Hard dependency, not just a nice-to-have**: this endpoint's contract already promises Spring Boot real per-asset guardrail bounds (`Asset.minDailyRate`/`maxDailyRate`) and correctly-resolved `category`/`condition`. Both require Phase 2a's real per-asset guardrail clamping and the `DB_NAME_TO_FEATURE_NAME` mapping fix (see "Category name mapping" cross-references above) — building this against `ml-experiments/predict_price.py`'s static-table stand-in would ship Spring Boot the wrong shape of data. Sequenced as `feature/ml-6-internal-pricing-api`, after `feature/ml-3-pricing-service`.

**Other decisions locked in the same discussion**:
- Spring Boot computes and sends `distance_km` directly (postal-code based) — Haystack does not geocode; real geocoding stays a Phase 2 non-goal either way. Open follow-up: sanity-check Spring Boot's real computed values against the synthetic training distribution, since the model was trained on a sampled proxy, not real distances.
- `deposit_rate` stays a fixed constant (0.30), returned in the response, not accepted as a request parameter — avoids adding request surface for a value that isn't currently asset/category-dependent.
- No `POST /internal/v1/pricing/estimate` (Spring Boot's original lightweight-pricing proposal) — dropped once the decision was made that the browse/detail page shows a flat, non-ML base price before checkout; no scenario needs live ML pricing before a quote exists.
- Quote audit fields: `model_version` + `was_clamped` persisted by Spring Boot; `raw_price` deliberately excluded — redundant when `was_clamped=false`, and even when clamped it's a model-calibration signal better tracked as Haystack-side monitoring than a permanent per-quote-item column in Spring's transactional schema.
- Recommend-price vs. later quote-price drift is intentionally left unreconciled — `period_utilization`/`lead_time_days` are live signals by design, so a later re-price legitimately differing from an earlier recommendation is expected, not a bug to fix.

### Phase 2d — retrain approach (locked 2026-08-12)

**Confirmed (2026-08-12): `Asset.minDailyRate`/`maxDailyRate` are meant to bound the price at any duration**, not a 1-day-only reference rate — resolving Option 2 from the change log's "guardrail/duration-discount scale mismatch found" entry above. This also settles Option 3 (making the clamp itself duration-aware): not needed — `model.py`'s existing clamp (`min(max(raw_price, min_rate), max_rate)`, applied identically regardless of `duration_days`) is already correct for this semantics, nothing to change there.

**Decided: proceed with Option 1 (retrain against a re-anchored synthetic dataset).** With the any-duration interpretation confirmed, the fix is squarely upstream in the training data: the model's duration-discount curve was calibrated without knowing it had to stay within a bound meant to hold at every duration, so it regularly predicts below `minDailyRate` for realistic multi-day rentals. Recalibrating the synthetic generator so the discount curve operates within the real guardrail band is now the correct fix, not a workaround pending further confirmation.

**Mismatch check is two separate knobs, not one number** — `ml-experiments/pricing_tables.py`'s synthetic price generation has two independent scale parameters, and "the scale is off" could mean either is wrong:
1. **`CATEGORY_BASE_RATE`** (`rate_at_min`/`rate_at_max` per category) — the base-rate anchor itself. Is it even in the right ballpark vs. real assets?
2. **`GUARDRAIL_MIN_RATIO_RANGE`/`GUARDRAIL_MAX_RATIO_RANGE`** (currently 0.28–0.35x / 1.15–1.30x of the base rate) — given a correct base rate, is this the right band width, or do real assets sit in a much tighter band?

Pull the comparison data from the **live `heavy_rental` DB (all 27 real assets)**, not `app/pipelines/seed_fleet.py` — that's the old 8-asset prototype fixture, already flagged elsewhere in this doc as superseded and too thin to trust for this kind of check.

**Implementation risk to guard against**: `generate_synthetic_data.py`'s `compute_price_per_day()` already clips the training target itself to `[base_rate * min_ratio, base_rate * max_ratio]` at generation time (not just at inference, like the production guardrail). `DISCOUNT_FLOOR = 0.35` deliberately sits right at the edge of today's permissive min-ratio range (0.28–0.35x) — the `pricing_tables.py` comment on `GUARDRAIL_MIN_RATIO_RANGE` says as much ("wide enough that the non-linear duration discount ... is not clipped away for most rows"). If `GUARDRAIL_MIN_RATIO_RANGE` is tightened to match a real floor much closer to 1x **without** also revisiting `DISCOUNT_FLOOR`/`DISCOUNT_RATE`, the generation-time clip will eat the duration discount during training itself — the model would then learn "price barely drops with duration," baking today's clamp-dominance problem into the model instead of fixing it. **`CATEGORY_BASE_RATE`/`GUARDRAIL_*_RATIO_RANGE` and `DISCOUNT_FLOOR`/`DISCOUNT_RATE` must be recalibrated together**, not the ratio range in isolation.

**Broken into three sub-phases plus a separately-gated promotion phase (2026-08-12)**, per explicit preference: keep the existing `synthetic_pricing_data.csv` and the git-tracked `app/services/pricing/artifacts/model.pkl`/`current.json` untouched throughout Phase 2d — every regenerated/retrained file is a new, versioned artifact alongside the originals, and promoting a candidate to production is a distinct, later-gated decision, not something training does automatically. (`app/services/pricing/model.py`'s loader is hardcoded to the literal filenames `model.pkl`/`current.json` — see "Architecture (Phase 2)" — so a differently-named candidate genuinely cannot affect live predictions until explicitly promoted; no accidental hot-swap risk.)

**Phase 2d-i — real-bound measurement** (analysis only, no code/data/model changes):
1. Pull real per-category `minDailyRate`/`maxDailyRate` distribution from the live `heavy_rental` DB (all 27 assets) — not `app/pipelines/seed_fleet.py`'s superseded 8-asset fixture.
2. Compare against `CATEGORY_BASE_RATE` (knob 1) and `GUARDRAIL_MIN_RATIO_RANGE`/`MAX_RATIO_RANGE`-implied bands (knob 2) separately. Output: a documented mismatch (the actual numbers), nothing else changes yet.

**Phase 2d-ii — recalibration + candidate build** (produces new versioned files only):
3. Adjust `pricing_tables.py`'s `CATEGORY_BASE_RATE` and/or `GUARDRAIL_MIN_RATIO_RANGE`/`MAX_RATIO_RANGE`, together with `DISCOUNT_FLOOR`/`DISCOUNT_RATE`, so the discount curve operates mostly *within* the recalibrated band rather than falling below it.
4. Regenerate synthetic data to a **new, versioned filename** — e.g. `generate_synthetic_data.py --output ml-experiments/data/synthetic_pricing_data_v2.csv` — leaving the Phase 1 baseline `synthetic_pricing_data.csv` untouched. Still gitignored either way, so this is purely a local naming convention, not a git-tracking concern.
5. Retrain a **candidate** via the production trainer's existing CLI flags — e.g. `app/services/pricing/train.py --data ml-experiments/data/synthetic_pricing_data_v2.csv --model-out app/services/pricing/artifacts/model_v2.pkl --meta-out app/services/pricing/artifacts/current_v2.json` — leaving the git-tracked `model.pkl`/`current.json` (currently serving live predictions) untouched. Optionally also rerun `ml-experiments/train.py` into `ml-experiments/artifacts/` to keep that scratch copy in sync for SHAP review (not required for production).

**Phase 2d-iii — candidate validation** (read-only comparison, no promotion):
6. Because the candidate isn't wired into `predict_price()`'s hardcoded load path, evaluating it needs a small standalone script: `joblib.load()` `model_v2.pkl` directly, reuse `feature_schema.build_features()` + the same clamp math `model.py` uses, and re-run the Phase 2a-style live check (all 27 real assets, durations 1/7/14/30 days) against it.
7. Compare the candidate's clamp rate at 7–14 days against the current production model's (today's baseline: 25/27 clamped at `duration_days=7`). **Gate for Phase 2e**: candidate must show a materially lower clamp rate at realistic durations without materially regressing MAE/R².

**Phase 2e — promotion** (new phase, gated on Phase 2d-iii passing, not part of Phase 2d's own scope):
8. Back up the current `app/services/pricing/artifacts/model.pkl`/`current.json` (rename to `model_v1.pkl`/`current_v1.json`) so the pre-calibration model stays recoverable.
9. Promote the validated candidate: copy/rename `model_v2.pkl`/`current_v2.json` → `model.pkl`/`current.json`, then call `reload_model()` (or restart) to hot-swap the in-process model.
10. Re-run the live Phase 2a check one more time through the real `predict_price()` path (not the standalone eval script) to confirm the promoted model behaves in production exactly as the offline candidate validation predicted.

### Phase 3 — seeding & retrain
- **Seed data ownership**: Spring Boot owns schema/migrations (source of truth for `Booking`/`Asset`/etc.); Python prototypes and inserts seed rows into that existing schema — faster to iterate on the numbers, doesn't create tables itself. Belongs in its **own spec** (`SPEC-domain-seed-data.md`), separate from pricing, since the schema is shared across other teammates' features too.
- **Retrain job**: **scheduled**, not just on-demand. In-process **APScheduler** inside the FastAPI app lifespan (no external cron/infra needed). Interval **configurable via env var** (e.g. `RETRAIN_INTERVAL_DAYS`, real default TBD — monthly vs. quarterly, pick one), overridable to a short interval for live demos. Persist last-run timestamp (in `current.json` or similar) so app restarts don't cause missed or duplicate runs. **Also** keep a manual "retrain now" endpoint as a fallback/demo safety net — cheap to add once the retrain logic exists.
- **Cold-start bootstrap → blend → cutover (Phase 1d design decision, riding on this same retrain job — not a new mechanism):** a fresh deployment has no real transaction history, but `period_utilization`/`lead_time_days` are always live-computable even with few bookings — what's missing is a learned price-response function that knows how to weigh them, and that still has to come from grounded synthetic data until real history accumulates.
  - **Bootstrap (now)**: 100% grounded synthetic data. Guardrail clamping (`Asset.minDailyRate`/`maxDailyRate`) bounds worst-case error in the meantime.
  - **Blend**: once real bookings start flowing through the scheduled retrain job above, extend its `train.py` call with sample weighting by data source/recency (`model.fit(X, y, sample_weight=...)`) — real rows weighted higher as volume grows. Real default weighting curve TBD, same "decide when you get there" status as the retrain interval above.
  - **Cutover**: per category, not all at once — each category (excavator, forklift, scissor lift, boom lift) drops its synthetic rows independently once it clears its own minimum real-sample threshold (exact threshold TBD). Categories graduate at different rates on purpose — e.g. forklifts likely accumulate real bookings faster than excavators, and there's no reason to hold every category to the slowest one's pace.
  - Restated (implementation-relevant contract only, not this full reasoning) in `openspec/specs/dynamic-pricing/design.md` ("Phase 3 — cold-start bootstrap, blend, per-category cutover").

| 2026-08-11 (guardrail/duration-discount scale mismatch found, same day) | **New finding, not yet resolved — needs a product/pricing-owner decision, not a unilateral code fix.** While live-verifying Phase 2a's `predict_price(...)` against all 27 real `heavy_rental` assets (the check described in the entry above), a systematic pattern emerged: at `duration_days=7` (a realistic rental length), 25 of 27 assets had their raw model output clamped **upward** to `minDailyRate` — i.e. the model's prediction was below the asset's real minimum rate almost every time. This isn't noise — it's consistent with a genuine scale mismatch between two things that were calibrated independently and never cross-checked until today: (a) the model's trained duration-discount curve (`ml-experiments/pricing_tables.py`'s `DISCOUNT_FLOOR`/`DISCOUNT_RATE` — price drops non-linearly for longer rentals, by design, down to ~0.35x at long durations, m(7)≈0.487), and (b) the real seeded `Asset.minDailyRate`/`maxDailyRate` values, which behave as if they represent a near-1-day rate floor/ceiling rather than a bound meant to hold across all durations. Put simply: the model correctly discounts a 7-day rental relative to a 1-day one, but the guardrail bound doesn't discount at all, so for any multi-day rental the clamp overrides most of the model's duration signal rather than lightly bounding it. **Why this wasn't visible earlier**: it took both a real per-asset guardrail (Phase 2a, today) and real per-asset bounds with actual variety (the reseed, also today) existing simultaneously to surface — the old static per-category guardrail table was too coarse to reveal a per-asset pattern, and the old 8-asset fixture was too thin to make the pattern statistically obvious even if someone had looked. **Not a Phase 2a defect**: guardrail clamping is doing exactly what `openspec/specs/dynamic-pricing/spec.md` requires — clamp raw output to `[minDailyRate, maxDailyRate]`. The defect, if it is one, is upstream: either the training data's duration-discount curve, the real assets' rate-bound semantics, or an unstated mismatch between the two that nobody had reason to check before real per-asset data existed on both sides. **Why it matters enough to flag rather than let ride**: it directly undercuts the reason richer seed data was pursued today (`openspec/specs/domain-seed-data/spec.md`) — if the guardrail clamp dominates at realistic rental durations, two assets with meaningfully different `condition`/`capacity`/`period_utilization` can still converge on the same clamped price (their shared `minDailyRate`), which is close to the exact "degenerate, non-differentiated pricing" problem the reseed was meant to fix. **Options on the table, none chosen yet**: (1) retrain against a synthetic dataset re-anchored so the model's short-duration prediction sits closer to `minDailyRate`/`maxDailyRate` as given, letting the discount curve operate mostly *within* the guardrail band rather than falling below it; (2) confirm directly with whoever owns the real `minDailyRate`/`maxDailyRate` values (Spring Boot / pricing policy) what they're actually meant to represent — a 1-day reference rate, or a bound intended to hold at any duration — since the right fix depends entirely on that answer; (3) reconsider whether duration-discounting should be allowed to push a prediction outside the guardrail band at all, versus scaling the discount to stay within it by construction.
